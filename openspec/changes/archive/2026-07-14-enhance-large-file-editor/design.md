## Context

当前 `FileEditorDocument` 以 32 KiB 分页、最多 3 页原始缓存的方式加载文件，文本只做 UTF-8 判断，搜索只扫描当前页。`FileEditorContentSource` 仅暴露大小、可写性、范围读取和完整内容流式替换，因此无法表达源版本、原地范围写入、另存为或协议能力差异。

编辑器需要同时覆盖 Local、Device、Share、Network 文件以及 Android、Desktop、iOS、JS、Wasm。实现必须保持内存有界、UI 不阻塞、远端请求可取消，并避免在大文件编辑、搜索、Hash、索引或统计时聚合完整文件。

## Goals / Non-Goals

**Goals:**

- 在所有平台提供一致的文本、搜索、定位、保存和分析语义。
- 对超大文件建立默认只读和有限编辑边界，并为所有保存路径提供冲突检测与可恢复性。
- 以后台任务、分块读取、有限缓存和增量索引保证大文件操作不会阻塞 Compose UI 或耗尽内存。
- 通过分阶段任务保持每个阶段可编译、可测试、可独立验收。

**Non-Goals:**

- 不提供原始字节编辑器或结构化字节编辑。
- 不在源文件目录写入索引、恢复或书签旁车文件。
- 不在本变更中重写现有文件传输协议；协议只需实现新增内容源能力契约。

## Decisions

1. **把内容源扩展为显式能力与版本快照。**

   新增 `FileEditorSourceCapabilities`，分别声明范围读取、等长范围写入、流式替换、另存为和原子替换能力；新增 `FileEditorSourceSnapshot`，包含大小、修改时间和内容源生成的不透明 revision/fingerprint。`replaceContent`、`writeRange` 和 `saveAs` 接收预期快照，内容源必须在写入前复核版本。

   备选方案是继续仅用 `canWrite` 并在编辑器内按协议分支。该方案会把协议细节扩散到核心编辑器，无法可靠决定原地保存和冲突检测，因此不采用。

2. **用访问模式和编辑能力分别表达安全状态。**

   所有可写源初始进入 `ReadOnly`；用户确认后才进入 `Editable`。文件大小达到 `1,073,741,824` 字节时，编辑能力固定为文本单页有界修改，解锁只在当前会话有效。

   备选方案是只对超大文件默认只读。统一只读入口能避免普通文件误触保存，并让 UI 和恢复逻辑只有一套状态机。

3. **文本编解码在 commonMain 中保持确定性。**

   定义 `EditorTextCodec`，支持 ASCII、UTF-8、UTF-16 LE/BE、GBK、ISO-8859-1。UTF 与单字节编码直接实现，GBK 使用仓库内的压缩映射资源，避免平台 API 对编码标签和替换策略不一致。检测顺序为 BOM、纯 ASCII、严格 UTF-8、UTF-16 启发式、GBK 启发式，最终回退 ISO-8859-1；结果携带置信度和 BOM 信息。

   用户选择了不可表示字符自动替换，因此编码器使用 `?` 或目标编码约定的替代字节，但保存预览必须列出替换总数和有限的位置样例。切换编码只改变解释方式；只有保存时才转换文件字节。换行检测跨块统计 CRLF、LF、CR，混合文件保持原字节，除非用户显式选择统一转换。

4. **把页面显示、行索引和搜索拆成独立后台管线。**

   页面继续使用 32 KiB 和有界 LRU 缓存，并在空闲时预取相邻页。正文到达顶部或底部后继续向可用相邻页方向拖拽时，界面显示跟随拖拽距离变化的上一页/下一页进度提示；达到阈值时提示变为“松开切换”，但只有用户松手后才发起分页并进入加载状态。桌面滚轮在边界使用相同提示，并以一小段滚轮空闲时间作为本轮滚动结束。松手或滚轮结束时未达到阈值则提示复位且不发起分页；加载提示跟随实际分页完成或失败结束，不使用固定延时隐藏。第一页向下拉或末页向上拉时不存在对应页面，因此不显示该方向的提示，也不产生分页请求。行索引按文件指纹持久化为稀疏检查点，默认每 4096 行记录一个字节偏移；首次打开立即显示第一页，后台边扫描边发布已索引范围。

   `LargeFileSearchEngine` 使用独立协程按块读取，精确文本搜索使用跨块尾部状态，正则使用有界重叠窗口并去重，单个正则匹配最大跨度为 1 MiB。结果按批发布，内存中最多保留 10,000 条明细，同时继续维护总数和进度。取消必须终止后续读取和远端请求。

5. **编辑日志与保存策略分离。**

   页级文本替换和有界命令日志支持逐步撤销/重做。日志记录字节范围、旧值摘要、新值和操作类型，不复制未修改文件内容。

   等长文本修改在内容源支持时使用范围写入，并先写被覆盖字节的回滚日志。其他修改流式写入临时目标，校验成功后原子替换或上传。普通文件默认保留完整备份；达到阈值的文件只保留被覆盖区域。保存失败必须保留编辑日志和原文件，恢复记录在保存成功或用户明确丢弃后清理。

6. **分析复用范围读取基础设施。**

   Hash 与统计作为可取消的后台流式任务，使用有界块读取并在源快照变化时丢弃过期结果。

7. **本机大数据与同步小数据分层保存。**

   行索引、恢复日志、备份、远端缓存仅存应用私有目录，并按源指纹和过期时间清理。最多 50 条搜索历史使用小型序列化快照接入现有设置同步，但采用新的 key 和数据类别。

8. **按两个阶段发布。**

   阶段一交付安全查看、文本展示、搜索、定位和文件信息；阶段二交付安全保存、恢复和统计。每阶段完成后都必须通过 common/JVM 测试和全部平台编译。

## Risks / Trade-offs

- GBK 映射资源会增加包体积 → 使用压缩双字节映射并在构建和跨平台测试中校验一致性。
- 正则可跨越任意长度，无法无限保留窗口 → 明确 1 MiB 单匹配跨度，UI 在启用正则时展示限制。
- 远端协议的修改时间可能不可靠 → revision 同时包含可用元数据与抽样内容指纹，无法验证时禁用原地覆盖并要求流式替换或另存为。
- 行索引、Hash、搜索、统计可能争抢 I/O → 使用每会话后台任务协调器限制并发，并让用户主动操作优先于预取和统计。
- 完整备份会占用大量空间 → 1 GiB 以上只存范围回滚日志，普通文件显示预计占用并允许在保存确认页关闭备份。
- Web 平台的私有存储配额有限 → 能力声明提供可用空间，无法创建恢复/临时数据时保持只读或要求另存下载。

## Migration Plan

1. 先扩展内容源契约和测试替身，在保持现有 `replaceContent` 行为可适配的情况下迁移各协议。
2. 引入访问模式、编解码、索引、搜索和信息面板，完成阶段一验收。
3. 新增保存日志、恢复存储和统计，完成阶段二验收。
4. 严格校验 OpenSpec、运行 core/shared 测试并编译全部目标。发生回归时按阶段回退；新表和私有缓存可以安全删除，现有文件系统书签不受影响。

None. 实现必须遵循本设计中的阈值、同步范围和正则跨度约束。
