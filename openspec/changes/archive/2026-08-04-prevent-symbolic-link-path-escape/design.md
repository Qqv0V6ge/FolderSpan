## Context

参见 [proposal.md](proposal.md) 的问题背景。当前 `FileSimpleInfo` 通过 Kotlin Serialization/ProtoBuf 在本地、HTTP 和 WebRTC 链路复用，但只暴露 `isDirectory`；JVM/Android 的 `File.isDirectory` 会跟随目录符号链接。多个递归调用方据此把链接加入队列，部分调用方还把全部发现条目保存在列表中。路径授权与链接分享则主要对未经解析的字符串做前缀或相对路径检查，权限判断和实际 IO 之间没有共享同一个真实路径边界。

实现必须继续覆盖 commonMain 及 Android、JVM、iOS、JS、Wasm source set，不新增外部依赖，并兼容缺少新字段的持久化数据和旧协议负载。对无法可靠判断链接状态的平台或旧对端，安全相关递归必须保守失败。

## Goals / Non-Goals

**Goals:**

- 给所有递归入口提供统一的“链接是叶子”判断，而不是让每个 UI 或任务单独猜测。
- 将授权根校验放在服务端实际 IO 边界，并让 HTTP 与 WebRTC 复用同一服务实现。
- 使本地统计只累计计数和大小，避免为属性对话框保留整棵目录树。
- 使普通、Root 和 Shizuku 删除都只删除链接目录项。
- 用可自动化的 JVM/公共测试固定路径逃逸、删除安全、循环终止和传输兼容行为。

**Non-Goals:**

- 不提供“跟随符号链接”用户选项；该能力需要单独的风险提示和目标去重设计。
- 不承诺在没有安全句柄式目录 API 的平台上彻底消除恶意并发替换路径造成的 TOCTOU；本变更在每次 IO 前重新校验并缩短窗口。
- 不改变云盘、对象存储或服务端本身没有符号链接概念的协议语义。

## Decisions

### 1. 在线路模型中同时记录链接值和可信状态

`FileSimpleInfo` 增加两个带默认值的新 ProtoBuf 字段：`isSymbolicLink` 和 `isSymbolicLinkKnown`。平台文件列举必须同时写入两者；旧数据和旧对端缺少字段时，`isSymbolicLinkKnown` 保持 `false`，从而能与“已确认不是链接”区分。`withCopy` 和所有协议映射必须保留两个字段。

本地路径调用方可以在元数据未知时用 `PathUtils.isSymbolicLink(path)` 重新确认；远端递归在未知且没有服务端安全递归保证时失败。选择两个布尔字段而不是单个 `isSymbolicLink = false`，是因为单字段会把旧端缺失字段静默解释为安全。选择字段而不是新枚举，可减少现有构造点和 ProtoBuf 映射的迁移范围。

### 2. `PathUtils` 提供平台真实路径边界原语

新增一个面向安全边界的 expect/actual 原语，输入授权根、候选路径以及是否允许不存在的最终叶子。各平台实现遵循以下步骤：

1. 规范化路径组件并拒绝 `..` 越界或仅字符串前缀相似的路径；
2. 将明确选择的根解析为真实根；
3. 从根之后逐组件检查符号链接，任何中间链接均拒绝；
4. 对已存在目标比较解析后的真实路径，对上传的新叶子比较最近存在父目录的真实路径；
5. 无法确认时返回失败，而不是放行。

JVM 使用 `java.nio.file.Path`、`toRealPath` 和 `Files.isSymbolicLink`；Android 使用 `lstat`/规范路径并逐组件检查；iOS 使用 Foundation 的标准化及链接解析能力；没有宿主符号链接的 JS/Wasm 内存文件系统执行严格组件边界检查。

备选方案是只调用 `File.canonicalPath.startsWith(root)`，但它既可能错误接受 `/share-backup`，也无法表达“共享根之下不经过任何链接”的策略，因此不采用。另一个方案是在每个路由内重复校验，会导致 HTTP/WebRTC 和上传/下载语义漂移，也不采用。

### 3. 授权服务接收已校验的安全路径

`DevicePathService` 在每个读取、写入、创建、删除和重命名入口中，先取得角色允许的根集合，再通过统一边界原语验证请求路径；双路径操作必须同时验证源和目标。`DeviceCertificateState` 仍负责策略数据和操作权限，但字符串比较改为路径组件比较，并由服务层执行符号链接解析。HTTP 与 WebRTC 控制器继续只委托该服务，不各自实现规则。

链接分享在会话建立时把用户选中的条目作为显式信任根。浏览、下载、批量归档和上传均通过同一解析器生成候选路径；共享根本身可以是用户明确选择的链接，但根以下任何链接不作为可进入的目录或上传父目录。

仅在客户端隐藏链接不足以构成安全边界，因为请求可被手工构造；因此最终拒绝始终位于服务端。

### 4. 递归收集器统一以链接作为叶子并支持流式消费

`collectDirectoryEntriesParallel` 继续作为文件任务和属性统计的公共入口，但在调用列举函数前拒绝链接根，在处理子项时只把 `isDirectory && knownNotSymlink` 的条目加入目录队列。本地适配器在字段未知时调用平台原语补全，远端适配器遇到未知状态则返回可诊断错误。

收集器保留两种模式：任务清单需要时保留条目，属性统计使用 `retainDiscoveredEntries = false` 并通过回调增量累计。队列和正在处理的批次受既有并发限制控制；只为防止非链接协议中的重复目录保留规范目录标识集合。Android 拖拽和 DocumentProvider 树遍历改为相同的不跟随/已访问集合策略，遗留 `PathUtils.traverse` 与 `Network.traverse` 同步收口，避免未来调用重新引入漏洞。

备选方案是在 `FileInfoDialog` 单独过滤链接，不能保护复制、删除、分享和未来调用，因此不采用。

### 5. 删除实现不得使用会跟随链接的便利递归 API

JVM 使用默认不启用 `FOLLOW_LINKS` 的 `Files.walkFileTree`，按后序删除普通目录，并把链接作为文件直接删除。Android 普通和特权后端在判断 `isDirectory` 之前执行 `lstat`，链接直接 unlink；普通目录才列举子项并后序删除。iOS 使用不跟随链接的逐项删除策略；JS/Wasm 保持内存文件系统的叶子删除语义。

不继续使用 `File.deleteRecursively()`，因为其目录判断会跟随链接，无法满足删除规范。

### 6. 测试使用真实临时目录验证目标未被触碰

JVM 测试创建“根内链接 → 根外目标”和祖先循环，分别验证元数据、统计、通用遍历、安全边界与递归删除。服务测试通过注入边界检查器覆盖 HTTP/WebRTC 共用服务的读写、删除和重命名拒绝。序列化测试验证旧负载解码为 `isSymbolicLinkKnown == false`，新负载在协议映射后保留字段。Android 无法在 JVM 上真实执行 Root/Shizuku 时，以后端契约测试和编译验证覆盖。

## Risks / Trade-offs

- [旧设备不发送可信状态，远端递归会被拒绝] → 提供明确升级提示；普通单层浏览仍可工作，升级对端后恢复递归任务。
- [某些平台创建新文件时目标尚不存在] → 解析最近存在父目录，逐组件拒绝链接，并在创建/替换前立即再次校验。
- [路径可能在校验后被恶意进程替换] → 每个实际 IO 入口重新校验；JVM 删除使用不跟随链接的 NIO 遍历。未来可在支持的平台引入句柄相对操作进一步缩小 TOCTOU。
- [把链接显示为叶子可能让复制链接本身的体验不一致] → 本变更优先保证不复制目标；不支持安全复制链接对象的平台返回明确错误，不退化为跟随链接。
- [新增字段会触及大量手工构造测试] → 字段提供兼容默认值，只有来自真实文件系统和远端递归的边界需要显式可信状态。

## Migration Plan

1. 先增加带默认值的线路字段及平台探测，确保新版本可读取旧数据。
2. 更新公共收集器、统计和文件任务；此阶段客户端已不主动跟随新端报告的链接。
3. 更新设备服务、链接分享与所有删除后端，把安全校验置于实际 IO 前。
4. 更新 Android 拖拽、DocumentProvider 和遗留遍历入口，消除旁路。
5. 执行公共/JVM/Android/JS/Wasm 编译及回归测试后发布；iOS 在 macOS CI 做最终原生编译。

回滚代码时无需迁移存储；旧版本会忽略未知 ProtoBuf 字段。但在包含安全修复的新版本和旧设备互操作时，新版本不得取消“未知即停止远端递归”的保护。
