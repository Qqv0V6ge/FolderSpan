## Why

链接分享页面当前通过 HTML `download` 属性、`Content-Disposition: attachment` 和 `application/octet-stream` 强制下载所有文件，导致 PDF、图片、音视频和文本等本可由访问浏览器原生显示的文件也无法直接查看。需要增加不依赖服务端转码的浏览器原生预览，同时保持现有下载、授权和共享路径安全边界。

## What Changes

- 在链接分享文件列表中仅为媒体类型属于保守浏览器原生预览范围的文件提供“在浏览器中打开/预览”入口；点击文件卡片主体或下载图标均触发下载。
- 引入明确的预览请求语义；服务端仅为符合预览资格的响应提供可确定的真实媒体类型、`Content-Disposition: inline` 和现有字节范围能力，由当前访问浏览器最终决定是否以及如何显示文件；未知或非展示型文件保持附件下载。
- 浏览器内联预览文本类型时显式声明 UTF-8 字符集，避免浏览器按本地默认编码猜测；服务端保持文件原始字节，不执行转码。
- 不根据 User-Agent 分支，也不维护按浏览器品牌划分的兼容格式列表；候选类型包括文本、常见图片/音视频和 PDF 等浏览器原生展示类别，并使用当前浏览器公开的 PDF 与音视频能力信号移除明确不支持的打开入口。
- 让单文件分享和目录内文件使用一致的预览响应规则，同时保持普通下载请求及 `X-API-Request` 客户端契约不变。
- 预览请求继续执行链接分享会话授权、隐藏文件过滤、磁盘分享权限、共享根真实路径和符号链接边界检查。
- 对可能包含主动内容的预览响应施加隔离策略，防止共享文件获得链接分享应用同源权限。
- 将打开与下载渲染为两个互不重叠的图标链接，并为每个图标提供独立且单层的 hover/focus 状态。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `browse-share-network`: 增加链接分享浏览器原生文件预览资格、浏览器能力最终决定显示结果、独立下载入口及预览安全隔离要求。

## Impact

- 主要影响 `core/src/commonMain/kotlin/com/folderspan/service/http/server/linkshare` 的文件响应分派、媒体类型与响应头策略。
- 需要调整 JVM、Android 和 iOS 的 `LinkSharePlatformFileResponder` 实现，使本地文件与远端共享文件遵循一致的预览/下载语义。
- 影响链接分享 HTML 文件卡片、SVG 图标和共享样式资源；不引入新的前端框架或文件转换依赖。
- 需要补充公共媒体类型策略测试、JVM 路由响应测试和 HTML 模板测试。
