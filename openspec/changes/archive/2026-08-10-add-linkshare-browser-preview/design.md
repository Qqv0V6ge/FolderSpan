## Context

链接分享路由当前由 `LinkShareRouteDispatcher` 统一执行访问设备识别、会话授权、共享 Disk 权限、隐藏文件和真实路径边界校验。目录页面中的文件卡片直接携带 HTML `download` 属性；文件请求最终进入 `downloadSharedFile`，远端文件响应固定使用 `application/octet-stream` 与 `Content-Disposition: attachment`，本地文件则委托 JVM、Android、iOS 的 `LinkSharePlatformFileResponder` 实现，但各平台同样默认返回附件。

现有响应流已经支持完整文件和 `Range` 字节范围，适合被 PDF 查看器和音视频播放器复用。主要约束是：

- 预览必须由当前访问浏览器的原生能力决定，而不是服务端按 User-Agent 猜测能力。
- `FileSimpleInfo.mineType` 在不同来源中可能是完整 MIME、`.ext` 扩展名或空值，不能直接作为规范化媒体类型使用。
- 普通下载、ShareNetwork API、批量下载、上传和路径安全契约不能因预览功能发生变化。
- 改动横跨 commonMain 路由/模板及 JVM、Android、iOS 本地文件响应，因此需要统一传递文件交付语义。

## Goals / Non-Goals

**Goals:**

- 仅让保守识别为浏览器原生预览候选的 PDF、图片、文本和媒体文件显示打开入口。
- 保留清晰、独立且向后兼容的附件下载操作。
- 对本地、Device 和 Share 文件提供一致的 MIME、内联处置及 Range 响应。
- 不削弱现有链接分享授权、隐藏文件、Disk 权限和真实路径/符号链接边界。
- 隔离能够执行主动内容的文件，避免其获得链接分享应用同源权限。

**Non-Goals:**

- 不实现自定义文件查看器、缩略图服务、Office/PDF 转换、媒体转码或内容编辑。
- 不通过 User-Agent、浏览器品牌或版本维护格式兼容表。
- 不保证某一种容器、编解码器或文件内容一定能被所有浏览器显示。
- 不改变 ShareNetwork API 客户端、批量下载脚本或上传协议。

## Decisions

### 1. 使用显式预览请求并保留原下载 URL

目录页为普通文件生成两个语义不同的入口：

- 预览：原文件路径加 `preview=1`，在新浏览上下文中打开，并使用 `noopener` 隔离 opener。
- 下载：文件卡片主体和独立下载图标都保持原文件路径及 HTML `download` 语义。

`LinkShareRouteDispatcher` 在完成现有授权和路径安全检查后才读取预览参数，并将请求归一化为 `Preview` 或 `Attachment` 文件交付模式。非 API 的单文件分享根请求使用 `Preview` 模式；未显式请求预览的直接文件请求以及 `X-API-Request` 请求保持 `Attachment` 模式。

选择查询参数而不是新增 `/preview` 路由，是因为文件路径已经由 fallback 路由、共享根匹配和路径规范化完整保护；查询参数不会引入第二套文件解析逻辑。备选方案是让所有文件请求默认内联，但这会破坏现有下载链接与 API 行为，因此不采用。

### 2. 媒体类型解析、预览资格与浏览器最终能力判断分层

增加统一的链接分享媒体类型解析器。解析顺序为：

1. 使用平台文件提供方返回的有效、非泛化 MIME，例如 Android `ContentResolver` 的结果。
2. 使用 `FileSimpleInfo.mineType` 中格式合法的完整 MIME。
3. 将文件名或 `.ext` 形式的 `mineType` 通过标准扩展名到 MIME 映射解析。
4. 无法可靠解析时回退到 `application/octet-stream`。

解析器先回答“响应的媒体类型是什么”，随后使用与浏览器品牌无关的保守类别和已知扩展名门槛决定“是否提供原生预览入口”：文本、常见图片/音视频以及 PDF、JSON、XML 等展示型类型可以进入预览流程，未知扩展名、`application/octet-stream`、可执行文件和其他非展示型应用类型只能下载。已知扩展名门槛优先采用保守结果，避免平台把 `.properties` 等未知文件泛化为 `text/plain` 后误开放入口。该门槛不会声称某个具体浏览器一定支持文件容器或编码；最终显示结果仍由当前浏览器决定。

服务端不会读取 User-Agent 来改变 MIME 或资格。前端不会把 `canPlayType()` 当作所有文件的总开关，但会将它用于其能够可靠回答的音视频候选；PDF 则使用浏览器公开的 PDF 查看器能力信号。文本、图片和其他展示类型仍由真实响应交给浏览器处理。

不读取文件内容进行 MIME 嗅探。这样可以避免为大文件预读数据，也与现有 `X-Content-Type-Options: nosniff` 安全策略一致。扩展名映射是媒体类型映射，不是浏览器兼容清单。

### 3. 预览与下载复用同一流式响应实现

文件响应构建器接收文件交付模式和已解析媒体类型：

- `Preview` 返回 `Content-Disposition: inline`。
- `Attachment` 继续返回 `Content-Disposition: attachment`。
- 两种模式都保留 `Accept-Ranges: bytes`、`Content-Length`、有效 Range 的 `206` 和 `Content-Range`。
- 文件名参数使用安全的 ASCII 回退和 RFC 5987 `filename*` 编码，避免非 ASCII 文件名丢失或响应头注入。

Device/Share 文件继续通过 commonMain 的范围读取流输出；本地文件接口增加文件交付模式及媒体类型提示，使 JVM、Android 和 iOS actual 能在打开各自文件流时返回相同的响应语义。这样不需要把平台文件句柄抽象迁入 commonMain，也不会复制浏览器判断逻辑。

### 4. 当前浏览器是最终能力判定者

通过预览资格门槛的响应始终携带服务端能够确定的同一媒体类型。Chrome、Safari、Firefox 或其他浏览器收到同一响应后，可以根据各自内置查看器、容器和编解码器能力选择显示、下载或提示无法打开。服务端不把具体浏览器的“不支持”转换为应用错误页，因为服务端无法可靠知道当前浏览器的真实运行能力。

`application/octet-stream` 和非展示型应用类型不具备预览资格：页面不生成打开入口，即使客户端手工添加 `preview=1`，响应也强制使用 Attachment。显式下载入口始终可用。

### 5. 主动内容使用响应级沙箱

媒体类型或扩展名表明文件可能包含主动内容时，例如 HTML、XHTML 或 SVG，预览响应增加独立的 `Content-Security-Policy`，至少包含不带 `allow-scripts`、`allow-same-origin` 的 `sandbox`，并禁止表单提交、基址改写和应用源网络访问。由于 `withCommonHeaders` 只补充缺失响应头，文件响应设置的更严格 CSP 可以覆盖通用页面 CSP。

若某个平台响应层无法保证该沙箱响应头，则主动内容强制使用 `Attachment`。安全分类同时检查声明 MIME 与文件扩展名；两者任一表明主动内容时都不能降级为普通内联响应。

备选方案是永久禁止 HTML/SVG 预览。响应级沙箱在满足“由浏览器原生打开”要求的同时允许静态内容显示，因此优先采用；附件回退仍作为无法隔离时的安全兜底。

### 6. 文件卡片拆分为可访问的独立操作

普通文件卡片使用语义容器：主要内容区域是下载锚点并展示文件信息，尾部操作区按资格显示独立的打开图标并始终显示下载图标，目录卡片保持导航行为。主体下载锚点通过卡片范围的点击层覆盖未被图标占用的区域，操作区使用更高层级避免命中主体链接；交互元素不嵌套、不相互遮挡，并保留键盘焦点、触摸目标和窄屏布局。预览入口文案使用“在浏览器中打开”，避免承诺浏览器一定能够显示。

打开和下载图标链接各自使用一个圆形 hover 状态层和强调色，但不附加 `ripple` 伪元素，避免同一图标出现两层状态背景。图标状态只由直接 `:hover` 触发，互不联动；链接同时保留 `:focus-visible` 轮廓，确保键盘操作可辨识。

### 7. 文本内联预览声明 UTF-8

媒体类型解析器继续返回不带参数的规范 MIME，供预览资格与主动内容判断使用。文件响应最终确定交付模式后，仅当交付模式为 `Preview` 且 MIME 属于 `text/*` 时，将响应媒体类型格式化为 `<mime>; charset=UTF-8`。附件下载、图片、音视频和应用类型不追加字符集参数。

该规则只告诉浏览器如何解释原始字节，不读取、替换或转码文件内容，因此不破坏流式与 Range 响应。非 UTF-8 文本仍可能由浏览器显示为乱码；支持任意本地编码需要可靠检测或显式编码元数据，属于自定义文本查看/转码能力，不在本变更范围内。

### 8. 页面入口与最终预览响应保持一致

页面与服务端都以已知扩展名映射作为保守预览基线。平台 MIME 提示若同样属于展示类型则保留；若平台提示是非标准或非展示型类型，但文件扩展名具有明确的规范预览 MIME，则预览响应使用扩展名映射，避免页面已经显示打开图标而响应又被服务端降级为 Attachment。

页面在初始化时进一步检查当前浏览器能够明确报告的能力：音频和视频使用对应媒体元素的 `canPlayType()`，PDF 使用 `navigator.pdfViewerEnabled`（存在时）。明确不支持时移除打开图标；API 不存在或无法可靠判断的展示类型仍交由浏览器按真实 MIME 最终处理。

由于共享脚本静态响应使用 immutable 缓存，页面引用 `share-index.js` 时附带本次交互实现的版本查询参数，使已访问过旧页面的浏览器不会继续执行缓存中的旧点击逻辑。

## Risks / Trade-offs

- [同一文件在不同浏览器中的结果不同] → 这是明确需求；UI 使用“在浏览器中打开”并始终保留下载操作，不承诺通用兼容性。
- [错误或缺失的文件元数据导致 MIME 回退] → 使用规范化优先级和扩展名映射，最终安全回退为 `application/octet-stream` 并仅提供下载，不进行内容嗅探。
- [HTML/SVG 等主动内容利用同源会话] → 使用不授予脚本和同源身份的响应级 CSP 沙箱；不能隔离时强制附件。
- [单文件分享从自动下载变为浏览器尝试打开] → 仅非 API 根请求改变交付模式，显式文件下载和 API 契约保持不变；可以通过恢复根请求的 Attachment 模式快速回滚。
- [平台 actual 行为不一致] → 为共同交付模式和媒体类型策略编写 common 测试，并为 JVM 路由覆盖完整、Range、内联和附件响应；Android/iOS 保持薄适配。
- [文本响应缺少字符集导致浏览器按本地编码猜测] → 仅对 `Preview` 的 `text/*` 明确声明 UTF-8，保持附件和响应字节不变。
- [页面显示打开入口但平台 MIME 导致服务端附件回退] → 对已知预览扩展名使用规范映射兜底，并测试响应仍为 inline。
- [服务端候选类型包含当前浏览器不支持的媒体容器] → 页面使用当前浏览器公开能力信号移除明确不支持的 PDF/音视频打开入口，无法判断时仍由浏览器最终处理。
- [浏览器 immutable 缓存继续使用旧交互脚本] → 更新页面中的共享脚本版本参数，确保新页面请求新的资源 URL。

## Migration Plan

1. 先引入媒体类型解析、文件交付模式和响应头单元测试，不改变默认页面行为。
2. 更新 commonMain 与各平台本地文件 responder，使 Preview/Attachment 两种模式均可用。
3. 更新目录模板、图标和 CSS，最后切换单文件分享的非 API 根请求为 Preview。
4. 运行 common/jvm 测试，并在至少两个具有不同原生能力的浏览器中验证同一文件的差异化行为。

该变更不涉及数据库或持久化数据迁移。回滚时可先移除页面预览入口并恢复单文件根请求的 Attachment 模式；新增响应参数和媒体类型解析器可以保留而不影响旧下载路径。

## Open Questions

无。已确认由当前访问浏览器决定文件是否以及如何显示，服务端不维护浏览器兼容格式列表。
